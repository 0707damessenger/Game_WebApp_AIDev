# Extract_Web_Reference

从网页、Wiki、游戏数据库等在线来源提取游戏信息，整理为结构化参考文档，存入 `docs/reference_games/`。

> **与 `Extract_Rulebook` 的关系**：Extract_Rulebook 处理 PDF 规则书，本技能处理网页来源。两者产出格式相同，可互补使用。

## 何时使用

- 用户提供了一个网页 URL，希望提取为参考文档
- 需要从 Wiki 或游戏数据库收集某款游戏的完整数据
- 需要对照多个来源补全已有参考文档中的缺失部分

## 操作步骤

### 0. 明确补全范围（Scope）

> **核心原则：先定义「要补什么」，再去搜索。目标越精确，token 消耗越低。**

在开始搜索前，必须先确定本次提取的范围类型：

| 范围类型 | 适用场景 | 搜索轮数 | 执行方式 |
|----------|---------|---------|-----------|
| **A. 全量提取** | 新游戏首次录入，需要规则+数据+策略 | 5-8 轮 | 轻量搜索 + 主流程整理 |
| **B. 规则补全** | 已有数据但缺核心玩法规则 | 3-5 轮 | 轻量搜索 |
| **C. 策略补全** | 已有规则但缺社区流派/攻略 | 2-4 轮 | 轻量搜索 |
| **D. 数据修复** | 特定字段缺失或错误 | 1-2 轮 | 轻量搜索 |

**如何判断范围**：
1. 若已有参考文档 → 先读文档，识别「缺什么」→ 选 B/C/D
2. 若无参考文档 → 选 A
3. 用户明确说了目标（如「补充策略」）→ 直接选对应范围，**不要自行扩大**

**关键约束**：
- **不要在用户要求「补策略」时去搜游戏规则细节**——那是浪费 token
- **搜索阶段优先使用轻量执行方式**——搜索任务不需要高成本深度推理
- **网络搜索/抓取操作无需询问用户确认**——这些是只读操作，应配置为自动允许

### 1. 识别数据来源类型

根据游戏类型和 URL 判断最佳来源：

| 游戏类型 | 首选来源 | 次选来源 |
|----------|---------|---------|
| **桌游/卡牌游戏** | BoardGameGeek (boardgamegeek.com) | 官方规则页、知乎/zhihu |
| **电子游戏（PC/主机）** | 官方 Wiki (fandom/wiki.gg) | Steam 社区、攻略站 |
| **手游/休闲游戏** | TapTap、攻略站 (ali213/gamersky) | 社区论坛 |

根据 URL 判断来源防护类型：

| 来源类型 | 典型特征 | 推荐策略 |
|----------|----------|----------|
| **MediaWiki 站点** | `*.fandom.com`, `*.wiki.gg`, `wiki.*` | → MediaWiki API 批量抓取 |
| **游戏数据站** | `ali213.net`, `gamersky.com` 等 | → curl 逐页抓取 |
| **Cloudflare 保护站点** | 返回 "Just a moment..." | → WebSearch 搜索引擎提取 |
| **普通网页** | 无特殊防护 | → WebFetch 直接抓取 |

### 2. 提取策略：并行优先，回退兜底

> **核心原则：不要串行等回退，能并行就并行。**

#### 策略 A：单一来源 URL
当用户只给了一个 URL 时，按回退链尝试：
```
WebFetch → curl → MediaWiki API → WebSearch
```

#### 策略 B：需要广覆盖（推荐，多数情况）
当需要完整了解一款游戏时，**并行启动多个渠道**：
```
┌─ curl 抓取用户给的 URL（获取该页面具体数据）
└─ WebSearch 广域搜索（获取多来源信息：官方 Wiki、攻略站、社区论坛、评测）
```
两路同时进行，结果合并后去重整理。这比串行快得多，且信息更全面。

#### 策略 C：多来源聚合
对于一款游戏，有价值的来源通常包括：

| 来源类型 | 典型站点 | 获取的信息 |
|----------|----------|-----------|
| 官方 Wiki | fandom.com, wiki.gg, hoodedhorse wiki | 完整游戏数据、卡牌/单位列表 |
| 桌游数据库 | boardgamegeek.com | 规则讨论、策略分析、卡牌数据 |
| 攻略站 | ali213.net, gamersky.com | 结构化图鉴、流程攻略 |
| Steam 社区 | steamcommunity.com | 玩家指南、策略讨论 |
| TapTap / 社区论坛 | taptap.cn | 中文攻略、流派分享 |
| 中文社区 | zhihu.com, bilibili.com | 深度策略讨论 |
| 评测站 | thexboxhub.com 等 | 设计分析视角 |

**搜索轮数与范围类型匹配——不要无差别搜 5 轮。**

### 3. 各渠道操作细节

#### 3a. WebFetch
```
WebFetch(url, "提取这个页面的所有游戏数据...")
```
- 优点：自动 HTML→Markdown 转换，AI 辅助摘要
- 常见失败：域名安全验证不通过

#### 3b. curl 直接抓取
```bash
curl -sL "URL" -o /tmp/page.html
```
- 优点：无域名限制
- 常见失败：Cloudflare JS 挑战（返回 "Just a moment..."）
- 后处理：需用 python3 解析 HTML 提取结构化数据

#### 3c. MediaWiki API（Wiki 站点专用）
```bash
# 列出所有页面
curl -s "https://WIKI_DOMAIN/api.php?action=query&list=allpages&aplimit=500&format=json"

# 批量获取页面内容（每次 50 页）
curl -s "https://WIKI_DOMAIN/api.php?action=query&titles=PAGE1|PAGE2|...&prop=revisions&rvprop=content&format=json"
```
- 优点：绕过 Cloudflare，获取完整 Wiki 源文本
- 适用于：`*.fandom.com`（api 路径 `/api.php`）、`*.wiki.gg`、`wiki.hoodedhorse.com` 等 MediaWiki 站点
- API 路径可能不同，常见变体：`/api.php`、`/w/api.php`、`/GAME_NAME/api.php`
- **必须保存原始数据**到 `docs/data_extracted/[游戏简称]/raw_wiki.json`

#### 3d. WebSearch 搜索引擎（兜底 + 广域覆盖）
```
WebSearch("site:DOMAIN keyword1 keyword2 ...")
```
- 优点：**总是可用**，不受任何防护限制
- 缺点：内容来自搜索摘要，可能不完整
- 策略：**按范围类型调整搜索关键词**

**按范围类型的搜索模板**：

| 范围 | 搜索关键词模板 |
|------|--------------|
| **规则补全** | `"GAME rules gameplay mechanics"`, `"GAME how to play turn structure"` |
| **策略补全** | `"GAME strategy guide builds"`, `"GAME best deck/build tips reddit"`, `"GAME 攻略 流派"` |
| **数据修复** | `"GAME CARD_NAME stats cost"` (精确查询) |
| **全量提取** | 以上全部 + `"GAME review design analysis"` |

**搜索语言策略**：
- **中文游戏**用中文关键词搜索（如「猫神牧场 攻略 流派 动物家族」），效果远优于英文
- **英文游戏**用英文关键词，但可补充搜索 `site:` 指定的 Wiki 域名
- **经典桌游**用英文搜 BoardGameGeek，再用中文搜知乎/B站补充
- **混合策略**：先用目标语言搜核心规则，再用英文搜评测/设计分析

### 4. 原始数据保存

对于大批量抓取（Wiki API 全量导出等），将原始数据保存到：
```
docs/data_extracted/[游戏简称]/
├── raw_wiki.json       # Wiki API 原始 JSON
├── raw_pages/          # 或逐页 HTML 文件
└── README.md           # 简要说明来源 URL 和抓取日期
```

对于小批量或搜索引擎提取，可跳过原始数据保存。

### 5. 整理为参考文档

按以下模板输出到 `docs/reference_games/[游戏名].md`：

```markdown
# [游戏名称] — 游戏数据参考

> **原名**：[English Name]
> **类型**：[类型标签]
> **开发商/发行商**：[...]
> **来源**：[来源站点名称 + URL]
> **提取日期**：[YYYY-MM-DD]

## 核心玩法规则
[最重要的部分！完整描述：]
- 局/场的基本结构（总共几回合、怎样算结束）
- 每回合/每轮的流程（按顺序列出每个阶段）
- 胜负条件与计分方式
- 资源系统（有哪些资源、怎么获取和消费）

## [游戏核心系统1]
[如：卡牌体系、建筑系统、战斗机制等]

## [游戏核心系统2]
[...]

## 完整数据表
[卡牌列表、单位列表等，使用 Markdown 表格]

## 已知策略/流派（如有）
[社区热门流派、构筑思路——这些信息对理解游戏设计深度至关重要]

## 设计亮点
[从游戏设计角度分析 3-5 个值得借鉴的独到之处]

## 与本项目的潜在关联
[该游戏的哪些设计理念可能对本项目有参考价值]
```

**重点原则**：
- **核心玩法规则是第一优先级**——一个不了解这款游戏的人读完规则章节后，应能理解游戏怎么玩
- 数据表力求完整（全部卡牌/单位/技能等），遗漏的要标注 `[待补全]`
- 使用简体中文撰写，专有名词保留英文原名
- 按游戏自身的系统逻辑分组（如按阵营/国王分组卡牌），而非一个大列表

### 6. 对照补全（可选）

当已有参考文档需要对照新来源补全时：

1. **先读现有文档，明确识别缺口**——不要盲目搜索，先列出「缺什么」
2. **确定范围类型**（步骤 0）——只搜缺的部分，不重新搜已有内容
3. **定向搜索**缺失内容（使用步骤 2-3 的方法，关键词聚焦缺口主题）
4. **就地更新**现有文档，而非创建新文件
5. 若补全结果影响正式设计判断，需在 `docs/design.md` 中记录引用关系与结论摘要

### 7. 完成与记录

- 参考文档属于 `docs/` 下的补充子文档，不得替代 `docs/design.md`
- 若本次提取结果被用于项目设计判断，必须更新 `docs/design.md`，补充引用关系与结论摘要
- 向用户汇报：提取了多少数据、文档行数、已知缺失项

## 实施规范

### 执行分工
- **搜索类工作**（WebSearch、curl 抓取、数据收集）→ 优先使用轻量执行方式，降低成本
- **整理类工作**（将搜索结果写入文档）→ 由当前主流程负责整理与输出质量

### 权限配置
以下操作应配置为**自动允许**，无需每次询问用户：
- `WebSearch` — 只读搜索
- `WebFetch` — 只读抓取
- `curl` — 只读网络请求
- 文件读写 — 写入 `docs/reference_games/` 和 `docs/data_extracted/`

如宿主环境支持自动允许配置，应将上述只读操作设为默认允许，避免打断主流程。

## 禁止模式

| 错误行为 | 正确做法 |
|---------|---------|
| 用户要求「补策略」时去搜规则细节 | 先定义补全范围（Step 0），只搜缺的部分 |
| 串行等待回退链（一个方法失败才试下一个） | 并行启动 curl + WebSearch，回退链作为兜底补充 |
| 搜索阶段使用高成本深度推理 | 搜索阶段优先使用轻量执行方式，整理阶段再做高质量归纳 |
| 一种方法失败就停下来询问用户 | 按回退链自动尝试下一种；WebSearch 是终极兜底，总是可用 |
| 中文游戏用英文搜索关键词 | 搜索语言匹配游戏语言；中文游戏用中文搜，桌游加搜 BGG |
| 只提取规则数据，忽略社区策略讨论 | 玩家流派/攻略揭示设计深度，是参考文档的重要组成 |
| 对照补全时直接搜索，不先识别缺口 | 先读现有文档，列出「缺什么」，再定向搜索 |
| 每次网络搜索/抓取操作都询问用户确认 | 只读操作应自动执行，不打断用户 |
| 大批量 Wiki API 抓取后不保存原始数据 | 原始 JSON 应保存到 `docs/data_extracted/` 方便重新解析 |
