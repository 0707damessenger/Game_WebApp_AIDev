# Find_Reference 技能说明

> **核心观点**（马晓轶）：
> 「一个参考本质上是既有的一连串决策的集合体。做一个好游戏要面对 1500 个不同层面的决策，至少做对 1200 个才能成功。找对参考 = 一次性做对一连串决策；找错参考 = 一次性做错一连串决策。」
>
> **推论**：大部分确定性低的事情都应该找参考。不存在凭空产生的创意，所有创意都是在某个参考基础上跨出一步。目标方向的难度高低 = 匹配参考的数量和匹配度。

---

## 参考类型总览

| 类型 | 核心问题 | 触发场景 | 触发方式 |
|-----|---------|---------|--------|
| **A. 游戏设计参考** | 做成什么样？有没有验证过这种体验有效的游戏？ | 设计新机制、确认体验方向 | 手动 / Plan_Design_Discussion 步骤 2-3 |
| **B. 方法论参考** | 怎么做？有没有成熟的设计框架/流程？ | 不会做某类设计、需要框架支持 | 手动 / Plan_Design_Discussion「不会做」缺口 |

## 执行流程

### Step 0：明确需求

搜索前回答：
1. **要解决什么问题？** — 一句话定义目标
2. **需要哪类参考？** — A/B（可多选）
3. **参考的应用范围？** — 全局性 / 关键机制 / 局部表现
4. **已有哪些候选？** — 先读 `source_quality_log.md`，优先用已验证的高质量来源

> ⚠️ 范围越全局，评估越严格。找错全局参考 = 全局决策全错。

---

### Step 1：按类型广搜候选

**搜索原则：只收集，不评估，在 Step 2 评估。**

#### Type A：游戏设计参考

**搜索方向**：同类游戏（直接竞品）+ 跨领域同基底 + 历史经典

| 来源平台 | 最适用场景 | 来源置信度基础 |
|---------|----------|------------|
| 已有 `docs/reference_games/` | 本项目已提取文档，优先 | 已评估，直接使用 |
| **Steam** 搜索 + 标签 | 当代游戏、玩家反馈 | 评论数 + 好评率 + 年份（见 Step 2） |
| **GDC Vault** (gdcvault.com) | 设计决策背后的思考过程 | 演讲者资历 + 会议年份 |
| **Metacritic / OpenCritic** | 跨平台质量对比 | 媒体评分 + 用户评分 |
| **BGG** (boardgamegeek.com) | 桌游机制参考 | 评论数 + 用户策略讨论质量 |
| **知乎 / Bilibili** | 中文玩家体验分析 | 需评估作者（见 Step 3 置信度信号） |
| **Extract_Web_Reference 技能** | 提取 Wiki 机制细节 | 基于 Wiki 质量 |

#### Type B：方法论参考

**搜索方向**：针对具体问题的框架/流程/最佳实践

| 来源平台 | 最适用场景 | 来源置信度基础 |
|---------|----------|------------|
| **GDC Vault** | 游戏设计方法论演讲（最权威） | 演讲者公司 + 内容具体性 |
| **Game Developer** (gamedeveloper.com) | 从业者写的设计流程文章 | 作者工作室背景 + 发布日期 |
| **Anthropic / OpenAI 官方文档** | AI 工作流 / Agent 设计 | 一手官方文档，高置信度 |
| **Microsoft Azure AI 架构中心** | Agent 设计模式 | 官方技术文档 |
| **GameDev.net 教程库** | 系统设计实践总结 | 作者发帖历史 + 社区回复质量 |
| **`Game_Design_Principles` 技能** | 已提炼的书籍框架 | 本项目内部，已验证 |
| **学术数据库**（ResearchGate/Google Scholar） | 方法论理论根源 | 引用数 + 期刊级别 |
| **知名咨询博客**（McKinsey、HBR） | 管理学框架（SMART、OKR等） | 机构权威性 |

### Step 2：三维评估

#### 维度一：匹配度（最重要）

**匹配度 = 解决问题的重合度 × 依赖堆栈的重合度**

**1.1 解决问题的重合度**（相似 + 差异，两者同样必须分析）

| 对比维度 | 我们 | 参考 | 相似 / 差异 / 差异根因 |
|---------|-----|-----|-------------------|
| 核心解决的问题 | | | |
| 提供的体验/效果 | | | |
| 目标用户/规模/平台 | | | |

> ⚠️「一拆二」原则：一个参考解决不了两个不同问题，必须分别找参考。
>
> 差异揭示借鉴边界。差异越大，需越谨慎，明确「能借鉴哪部分，不能借鉴哪部分」。

**1.2 依赖堆栈的重合度**（游戏参考专用）

| 层级 | 说明 | 我们 | 参考 | 重合度 |
|-----|-----|-----|-----|-------|
| **依赖基底（1）** | 缺了游戏不成立的核心机制 | | | 完全 / 部分 / 否 |
| **协同模块（0）** | 放大效果的辅助系统 | | | 高 / 部分 / 否 |

> 基底不重合 → 参考价值极低，无论表层多像。基底决定「能否参考（0 or 1）」，协同模块决定「效果放大程度」。

**方法论参考的匹配度**（Type B 专用）

| 对比维度 | 我们 | 方法论 | 匹配？ |
|---------|-----|------|------|
| 设计问题类型 | | | 是/否/部分 |
| 适用团队规模/阶段 | | | 是/否/部分 |
| 技术/工具依赖 | | | 是/否/部分 |

**匹配度评级**：
- **高**：基底重合 + 解决问题高度重合（差异在表现层）→ 核心参考，深入研究
- **中**：基底重合但问题有偏差，或问题重合但基底有差异 → 参考局部，明确边界
- **低**：表层相似但基底或核心问题不重合 → 谨慎引用，标注差异限制

---

#### 维度二：先进性

**在同类参考中，这是否是当前最先进/权威的？至少对比一个替代参考。**

**游戏参考 — Steam 量化指标**（三项同时满足才算强参考）：

| 指标 | 强参考阈值 | Steam 官方标准 |
|-----|---------|-------------|
| 评论数 | ≥ 1000 | 500+ 可信；1000+ 可靠；< 100 波动大 |
| 好评率 | ≥ 80% | 80%+ Positive；85%+ Very Positive；95%+ Overwhelmingly |
| 发布年份 | 2021+（近5年） | 经典例外需说明 |

> 不适用 Steam 标准的情况：主机独占、历史经典（10年+已验证）、独立原型（机制验证充分）。

**方法论参考先进性**：GDC 演讲 > 知名设计师著作 > 主流游戏媒体 > 个人博客；方法论迭代较慢，2015 年前的经典框架（如 MDA）仍有效。

**先进性评级**：领先 / 同期水平 / 已过时（有更好替代）

---

#### 维度三：性价比

**性价比 = 借鉴价值 ÷ 实现成本**

借鉴价值（对核心支柱的直接支撑程度）÷ 实现成本（设计复杂度 + 工程复杂度 + 玩家学习成本）

```
          高借鉴价值
               │
  必要的攻坚   │   必摘的果子
 ──────────────┼──────────────
  绝对不做     │   ①②做完再看
               │
          低借鉴价值
    高实现成本 ←─────────────→ 低实现成本
```

> 借鉴价值不确定时，明确标注「待验证」，不假装确定。

### Step 3：来源置信度评估（Source Quality Review）

**目的**：评估「这个来源本身是否可信」，独立于三维评估。

**快速判断框架（SIFT）**：
- **S (Stop)**：发布方/作者是谁？第一印象？
- **I (Investigate)**：作者背景是否与主题相关？
- **F (Find Better)**：有没有更权威的来源说了同样的事？（横向验证）
- **T (Trace)**：关键主张是否有原始出处？

**各平台置信度信号**：

| 平台 | 高置信度信号 🟢 | 低置信度信号 🔴 |
|-----|-------------|-------------|
| **知乎** | 机构/专业认证徽章；赞同 500+；粉丝 1万+；工作/教育信息完整 | 匿名/无认证；纯主观感受无数据 |
| **GDC Vault** | 知名工作室演讲者；近5年；有具体数据/案例 | 早期内容无后续验证；演讲者背景不明 |
| **Reddit** | 评论者有长期发帖历史+开发经验；被同行认可 | 高赞 ≠ 准确（共鸣 ≠ 技术正确）；新账号 |
| **Steam 社区指南** | 作者游玩 200h+；有效评论讨论；多人点「有帮助」 | 0评论；作者游玩极短；明显利益导向 |
| **个人博客** | 有可查游戏作品/从业履历；有数据/截图支撑 | 无作者简介；纯观点无论据 |
| **学术论文** | SCI/SSCI 收录；引用 50+；近3年 | 无法查验的期刊；零引用 |
| **Bilibili** | UP认证+粉丝 10万+；高质量讨论弹幕/评论；有实操依据 | 纯观点向；无数据；娱乐性强 |
| **官方文档**（Anthropic/OpenAI/MS）| 一手来源，直接可信 | 版本过旧、非官方镜像 |

**置信度评级**：
- 🟢 **高**：多个高置信度信号满足，可直接引用
- 🟡 **中**：部分信号满足，引用时需交叉验证
- 🔴 **低**：信号缺失或有红旗，需寻找替代来源

### Step 4：产出参考清单与佐证存放

**游戏参考清单**：

```markdown
| 参考 | 具体机制 | 相似之处 | 差异/边界 | 匹配度 | 先进性 | 性价比 | 置信度 | 佐证链接 |
|-----|---------|---------|---------|-------|-------|-------|-------|---------|
| [游戏]（年/好评率/评论数）| [机制] | [相似] | [差异] | 高/中/低 | 领先/同期/过时 | 必摘/攻坚/再看/不做 | 🟢/🟡/🔴 | [URL] |
```

**方法论参考清单**：

```markdown
| 来源 | 解决的问题 | 关键方法摘要 | 适用边界 | 置信度 | 佐证链接 |
|-----|----------|-----------|---------|-------|---------|
| [GDC演讲/文章] | [问题] | [方法] | [适用/部分/需调整] | 🟢/🟡/🔴 | [URL] |
```

**主契约关系**：

- 参考清单属于分析过程产物，不得替代 `docs/design.md`
- 若参考结论被用于正式设计判断，必须同步更新 `docs/design.md`
- 如同时产出了 `docs/reference_games/` 或 `docs/plans/` 子文档，必须在 `docs/design.md` 中补充引用关系与结论摘要

**佐证（URL）存放规则**：

| 场景 | 存放位置 | 格式 |
|-----|---------|-----|
| Skill / Workflow 文档的方法论依据 | **内嵌在该文档的「理论来源」区块** | `> 📎 [名称](URL) — 🟢置信度 — [关键支撑点]` |
| Plan 文档中的方案参考依据 | **内嵌在对应方案描述中** | 同上 |
| Changelog | **不存储 URL**——仅记录「执行了 Find_Reference，产出见[文档名]」 | 一行文字 |
| 来源质量长期积累 | **`source_quality_log.md`（持久化）** | 见下节 |

---

### Step 5：强制后置——Source Review 并更新 source_quality_log.md

> ⚠️ **强制步骤**，每次 Find_Reference 执行后自动执行，不需要用户指令，不可跳过。

执行动作：
1. 列出本次使用的所有来源
2. 对每个来源用 Step 3 的信号打分
3. 更新 `source_quality_log.md`：新来源 → 添加条目；已有来源 → 更新评分和备注
4. 如发现某来源与后续讨论结论矛盾 → 主动降级该来源评分，注明原因

## 自我迭代机制（Self-Improvement Loop）

**核心设计原则：AI 自主持续进化，不依赖用户每次指导。**

**自动触发规则**（AI 主动执行，无需用户提示）：

| 触发事件 | AI 自动执行的动作 |
|---------|---------------|
| Find_Reference 执行完成 | 执行 Step 5，更新 source_quality_log.md |
| 后续讨论发现某参考结论有误 | 降级 source_quality_log.md 中对应来源，备注原因 |
| 发现新高质量来源 | 添加到日志，标注「待验证」；累积 2 次验证后升为「已验证🟢」 |
| 同一类型来源被多次证明不可靠 | 在 `source_quality_log.md` 中补充平台风险说明与筛选备注 |
| 发现某类问题缺乏搜索来源 | 在 `source_quality_log.md` 记录该盲区，下次提前警示 |

**自我迭代的核心资产**：`source_quality_log.md`
→ 跨会话持久化的「来源质量数据库」
→ 每次 Find_Reference 执行前必须先读取，优先使用已验证的 🟢 来源
→ 不需要用户教才能进步，AI 通过使用 + 反馈自动积累

## 参考缺口警告

- 🚨 **零参考警告**：核心机制完全无参考 → 信仰之跃风险，建议先调研或调整方向
- ⚠️ **低匹配度警告**：现有参考匹配度均低 → 机制方向可能需要重新审视
- ⚠️ **过时参考警告**：现有参考先进性为「已过时」→ 建议升级参考
- ⚠️ **低置信度警告**：所有来源置信度为 🔴 → 需寻找更权威来源再决策

## 禁止模式

| 错误行为 | 正确做法 |
|---------|---------|
| 只分析相似性，不写差异/边界 | 匹配度必须同时输出相似 + 差异（两列） |
| 引用基底不重合的游戏参考 | 验证依赖基底是否重合 |
| 用单一参考覆盖两个不同问题 | 一拆二：分别找参考 |
| Steam 参考不附评论数/好评率 | 三项指标（数量/比率/年份）必须同时给出 |
| 找完参考不做 Source Review | Step 5 不可跳过 |
| 把 URL 塞进 changelog | URL 放文档行内引用或 source_quality_log.md |
| 每次从零开始找来源 | 先读 source_quality_log.md，优先用已验证🟢来源 |
